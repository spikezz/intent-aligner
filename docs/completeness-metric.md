# 信息完备度：一次调用拿到的信息够不够

这个度量对工作流里的每一次 LLM 调用回答一个问题：完成这次调用的任务所需要的信息里，提示词提供了多少，是以什么形式提供的。它不看模型答得对不对，只看信息到没到。

每个调用读到什么写在 [workflow.md](workflow.md) 的“context 的组装”一节，每个调用读不到什么写在 [call-blind-spots.md](call-blind-spots.md)。那两份文档是读代码得出的；这份文档描述的度量用来验证它们。

## 四个对象

| 对象 | 含义 | 由谁产生 |
|---|---|---|
| 任务实例 | 这次调用的任务说明（system prompt）、回答格式、`<header>`，以及它处理的对象 | 取自调用记录 |
| 语料 | 原始 session 截到这次调用的时间界限为止，每条记录的每个内容块是一个文本文件，字符坐标稳定 | 代码 |
| 需求集 | 完成这个任务实例所需要的全部信息，每条指回语料里的字符区间 | 挖掘模型 |
| 提供状态 | 需求集里的每一条在实际发出的提示词里处于什么状态 | 代码，加本地模型的一步判断 |

挖掘模型看不到实际发出的提示词、窗口和压缩结果。它的任务不是完成原任务，而是回答“要正确完成原任务，需要原始会话里的哪些信息，一条都不能漏”。

## 语料

语料是 session 的原始记录，包括管线不读的内容，这样“被过滤规则排除”也能被度量出来。

| 记录 | 是否进语料 |
|---|---|
| 用户和 AI 的发言、AI 的思考、工具调用、工具结果 | 进 |
| 用户在 AI 工作时打的字（`queued_command` 附件） | 进，算用户发言 |
| 运行程序在会话进行中附给 AI 的内容：每轮提醒、文件变动通知 | 进，来源记为 `harness` |
| 运行程序在会话开头给 AI 的内容：系统提示词快照、指令文件、技能和工具列表、环境信息 | 不进，它们是配置 |
| 事后写入的派生记录：`ai-title`、`last-prompt`、`system`（含离开摘要） | 不进 |

时间界限是本地模型那次提示词取材的最晚一条原始记录：通常是当前单元；切分发言段落时是整次发言的末尾；调用 G 是 `<此后的对话>` 的最后一项。发言记录按文件顺序截断，并检查界限前后的时间戳和文件顺序一致；`harness` 记录和它伴随的消息时间戳相同，所以按时间戳截断。语料里的邮箱地址替换成 `<email>`。

## 需求集

每条需求有五项：

- `fact`：这条信息是什么，一句话。
- `use`：原任务的哪一项判断要用到它。
- `role`：`object` 是任务处理的对象本身，`context` 是对象之外、用来理解或判断对象的信息。
- `grade`：`decisive` 表示缺了它答案会变或无法确定，`supporting` 表示它只让答案更确定或排除另一种解读。
- `occurrences`：这条信息在语料里出现的每一处。一处是一个片段列表，片段是 `file`、`start`、`end`（Unicode 字符下标，左闭右开）。

需求按条计数而不按字符计数，因为同一条信息可能出现多次（提示词里有一处就够），而一句很短的话可能决定整个判断。任务需要但语料里没有的信息单独列在 `missing` 里。

## 打分

一条需求在实际发出的提示词里有五种状态，有多处出处时取最好的一处：

1. 原文在：出处的文字逐字出现在提示词里。
2. 压缩形式保住了：原文不在，它所在的记录以压缩形式在提示词里（第一级概括、轮次概括、节点 label、聚合观测），并且压缩后的文字仍然包含这条信息。
3. 压缩形式丢了：压缩形式在，但这条信息没有保留下来。
4. 不在：这条记录是管线的处理单元，但提示词里没有它的任何形式。
5. 被过滤：这条记录不是管线的处理单元。

状态 1、4、5 由代码在提示词里查找确定。状态 2 和 3 的区分是语义判断，由本地模型池回答“这段压缩文字是否包含这条信息”。

完备度只算 `role` 为 `context` 的需求，因为对象本身必然在提示词里，计入分母会稀释上下文的缺失：

- 严格完备度 = 状态 1 的需求数 ÷ 全部需求数。
- 宽松完备度 =（状态 1 + 状态 2）÷ 全部需求数。

两个数按 `grade` 分开报，按调用种类汇总。状态 3、4、5 的需求列成缺失清单，按信息类别汇总，用来决定哪类信息该放进提示词，哪类该放进索取出口。

需求集只取决于任务实例和语料，不取决于提示词怎么拼。改窗口、改压缩或打开索取出口以后，只要调用还是同一个任务实例，只需要重新打分。

## 需求集的检查

- 每个片段在文件范围内、非空。
- 本地模型的回答引用过的原文（意图和边的 evidence）应当被需求集覆盖；没有覆盖的要逐条看是挖掘模型漏了，还是本地模型引用了无关内容。
- 对一部分调用独立挖两遍，看两份需求集和等级的重合程度。

## 挖掘模型的隔离

挖掘用 Codex（`gpt-6.1-sol`，xhigh），通过 `workspace/tools/agent_chat_log/chatlog.py` 发起，每个调用一个新的案例文件夹和一个新的日志目录。日志目录放在 `llm-home/chatlog/<运行名>/<序号-调用>`，和其他后端的调用记录在一起。全部设置用 `init --codex-config` 临时传入，不改 `~/.codex` 的配置：

| 设置 | 作用 |
|---|---|
| `init --no-history` | 第一封信不附带发起方的对话历史 |
| `init --ephemeral` | Codex 不在 `~/.codex/sessions/` 留会话文件，度量的会话不混进日常的 Codex 对话；日志目录是唯一的记录，每个目录只发一封信 |
| `permissions.corpus.filesystem={":minimal"="read",":workspace_roots"="read","~/.codex/packages"="read","~/.codex/memories"="deny"}`、`default_permissions="corpus"` | 命令只能读案例文件夹，不能写，不能联网 |
| `approval_policy="never"` | 不能申请跳出沙箱 |
| `features.memories=false`、`features.apps=false`、`features.plugins=false`、`mcp_servers.<name>.enabled=false` | 关掉记忆、连接器、插件和 MCP，它们在 Codex 进程里运行，不受沙箱限制 |
| `model_instructions_file=<几行的说明>` | 换掉人格文件，减少每次请求的固定输入 |

案例文件夹放在仓库之外（`/media/spikezz/v/Project/intent-aligner-completeness/<运行名>/<序号-调用>`），因为 Codex 会把工作目录所在仓库的项目文档放进提示词。文件夹里有 `corpus/`、`task/`（任务说明、回答格式、header、处理对象）和 `tools/span.py`（查字符坐标）。
