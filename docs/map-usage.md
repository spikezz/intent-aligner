# 意图地图的使用与修正

本文档定义意图地图被抽取出来以后怎样使用、怎样在使用中修正，以及这种用法反过来对抽取提出的约束。地图的概念和存储格式定义在 `docs/trajectory-extractor.md`，抽取流程定义在 `docs/workflow.md`。这两份文档和本文档冲突时，以本文档对“地图要满足什么”的要求为准，再去改抽取。

## 目标

意图地图是 agent 进入过往对话记录的起点。agent 读着地图就能掌握一个问题的全局，也就是所有相关 session 里和它有关的部分，再沿着地图回到原文，取出当时探讨或解决这个问题的完整细节。

衡量地图是否达到目标的任务是这样的：用户说“把我们之前生产两个视频的完整可复用流程整理出来，跳过第一次开发时的摩擦”，agent 能轻易完成。完成的路径应该是这样的：

1. 在地图上找到和视频生产有关的用户意图。
2. 沿 `serves` 找到为它们服务的意图和聚合。
3. 只保留最终有 `satisfies` 的那条路径，丢掉被 `blocks` 之后改道的分支。“跳过摩擦”在这里是一个图上的操作，这正是地图比全文搜索强的地方。
4. 沿节点和边指回原文的位置，读出具体的命令、参数和顺序。

## 入口：整张地图放进 agent 的上下文

地图不配查询命令。agent 的入口就是把整张地图读进自己的上下文，因为 agent 本身能读文件、能沿着指针跳到原文，所以不需要另一层检索。

由此得到地图最硬的一条约束：**整张跨 session 的地图必须放得进 agent 的上下文**。每个节点、每条边花多少 token，都要按这条约束来衡量。

## 地图是跨 session 的

地图的范围是全部语料，不是单个对话。一个问题往往分散在好几个 session 里，比如“让被阻塞的 run 重新跑起来”在 MV 项目里前后出现在多个 session 中。只有在构建时就把它们认成同一个节点，agent 才能在地图上看到这个问题的全局。事后把各个对话的图谱拼起来做不到这一点，因为同一件事在不同图谱里编号不同、措辞也不同。

所以 topic 登记表和图谱要在 session 之间延续，抽取的指针按时间顺序走过所有 session。概念文档里“一个 topic 可以延续好几个 session”的定义就是为此准备的。

## 在使用中修正

地图不要求一次抽对。agent 从地图出发读原文、继续探索，在这个过程中发现地图的错误，再回头修正地图。地图靠使用收敛。

这个用法决定了抽取工作的优先级：

- **覆盖、指回原文的位置、放得进上下文，比单条边的精确更重要。** 一条边连错了，agent 读原文时会发现并改掉。可是一个问题在地图上完全没有节点，或者节点指不回原文，agent 就没有起点。所以对于“这条模糊的边该不该连”这类问题，抽取用简单的规则处理就够了，不值得让模型为它反复权衡。模型反复权衡还会导致思考顶满，耗时也会成倍增长。
- **抽取宁可多登记节点，也不要漏。** 修正只发生在 agent 走过的地方。一个问题如果在地图上没有任何痕迹，agent 除非碰巧读到那段原文，否则不会发现它缺失，所以遗漏是唯一不会在使用中自动收敛的错误。

修正要满足三点：

- **修正是叠在抽取结果上面的独立一层。** 抽取是串行的，后面每一步的提示词都依赖前面的边。所以直接改抽取结果会有两个后果：重跑抽取会把修正覆盖掉，而且后面的步骤是在旧的边上生成的。修正单独存放，重跑抽取不会丢失修正。
- **每条修正都带着依据。** 一条修正要记录改了什么、依据哪段原文，以及 agent 是在做什么任务时发现的。这样修正本身可以被审查。
- **修正记录是抽取质量的数据。** 每一条修正都是一个“抽取错在哪里”的样本，而且带着原文证据。改抽取提示词时，优先看修正记录里反复出现的错误。

## 地图的体积

在 claude-87eeb4bd 的 qwen-schema 整轮里，第 101 个单元所在 topic 的图谱有 30 个节点、54 条边。按 Qwen 的分词器计算，它的体积如下：

| 部分 | token |
|---|---|
| 整张图谱 | 5,928 |
| 其中边的原文证据 | 1,810 |
| 其中 9 个聚合观测的标签 | 1,260 |

这个对话合并后有 438 行，而语料里 12 个合并对话一共约 50 万行。按行数粗略外推，全部语料的地图在几百万 token 的量级，所以按现在的形式放不进上下文。缩小体积的办法要按信息的性质来分：

**原文证据换成指针，这是无损的。** 证据是原文的原样摘录，抽取时代码会校验它确实出现在原文里，所以可以机械地换成字符位置，不需要再问模型。指针的形式是“消息编号加字符区间”的列表，原因有两个：一条证据可以用 … 分成几个片段，而且片段可以来自此前的对话，也就是和这条边的段落不在同一条消息里。目前每条边已经有 `span` 编号，span 记录了来源消息，发言段落还记录了字符区间 `chars`；证据本身仍然存的是文字。

**聚合观测的标签不压缩。** 证据是原文的复制品，换成指针不丢任何东西。聚合观测则是对一串工具结果的概括，原始的工具输出往往很长，而且分散在很多次调用里，这段概括是地图上唯一说明“这一串操作查到了什么、做成了什么”的地方。它在两个阶段都不可替代：

- 在抽取阶段，后面的调用看不到早先工具结果的原文，只能靠它判断聚合是完成了还是受阻了，它也是 `triggers` 边的起点。
- 在使用阶段，没有它，agent 就要把一个聚合下的每次工具调用都读一遍才知道结果，而这正是地图应该省掉的路。

聚合观测里混进了对“做到了哪一步”没有贡献的细节，比如文件的行数和字节数、每个任务的耗时秒数。这属于概括写得好不好的问题，要靠改抽取时写概括的提示词解决，不能作为事后截短它的理由。

**定位不靠标签。** 地图上的一个节点在原文里的位置，由段落的消息编号和字符区间确定；`satisfies` 和 `blocks` 边的证据直接是工具调用的编号。标签的作用是内容，不是定位。

## 现状和目标的差距

| 目标需要的能力 | 现状 |
|---|---|
| 地图覆盖全部语料 | 只挖过两个对话，claude-87eeb4bd 被反复跑了多轮，用来调抽取质量 |
| 跨 session 的同一个问题是同一个节点 | 每个对话各跑一轮，每一轮都从空图谱开始，对话之间没有连接 |
| 整张地图放进上下文 | 证据仍然是文字；全语料的体积远超上下文 |
| 节点和边指回原文 | 边和段落已经能指回消息和字符区间；证据还没有换成字符位置 |
| 使用中修正 | 没有修正层，也没有修正记录的格式 |

## 未决问题

- **整张地图仍然放不下时怎么办。** 证据换成指针只能省掉约三成，剩下的都是内容本身。一个可能的做法是分层：最上层放 topic、意图和聚合的标题，这一层整张进上下文；聚合观测这类概括按 topic 展开，agent 走到哪个 topic 再读哪个 topic 的完整图谱。这个做法还没有定，它和“整张地图进上下文”的要求之间的取舍要由用户决定。
- **跨 session 的抽取怎么跑得完。** 全程串行时，一个对话的一百多个单元就要跑几个小时，约 50 万行的语料用这种方式跑不完。不同 session 在时间上还会交错，指针按时间顺序走时，同一时段可能有几个 session 并行推进。
- **修正层的格式。** 修正存在哪里、怎样和抽取结果合成 agent 读到的那张地图、抽取重跑后节点编号变了时修正怎样对上，都还没有定义。
