# 每个调用读不到的信息

每个调用读到什么，写在 [workflow.md](workflow.md) 的“context 的组装”一节。这份文档列出相反的一面：运行时我们手里存着、但某个调用读不到的信息，以及这项信息对这个调用的判断有没有用。“有没有用”一栏是读代码和提示词得出的判断，没有用实验验证过。

## 我们存着的信息

| 信息 | 存在哪里 | 现在谁能读到 |
|---|---|---|
| 发言的原文 | 时间线上的项（`units.Speech`），topic 存储的段落（span）记着每个意图节点出自哪一段 | 窗口内的调用；发言离开窗口以后，没有调用再读它 |
| 工具调用的原文 | 时间线上的项（`units.ToolCall.text`） | 只有第一级压缩 |
| 工具结果的原文 | 时间线上的项（`units.Observation.text`） | 只有第一级压缩 |
| 每次工具调用的意图和操作对象、每个结果的概括 | `digests.jsonl` | 窗口内逐条给出；离开窗口或被轮次概括代替以后，没有调用再读它 |
| 每次工具调用归入了哪个聚合 | topic 存储里工具调用段落的 `aggregates` | 没有调用读到：窗口里的工具调用不标聚合编号 |
| 每个聚合已有的底层意图 | topic 存储的 `meta.tool_intents` | 只有调用 L，并且只有当前这一个聚合的 |
| 当前单元之后的内容 | 时间线上后面的项 | 只有调用 G（`<此后的对话>`），以及切分和段落处理时同一次发言的后文 |
| 其他 topic 的图谱 | 各 topic 的存储 | 只有切分和调用 T |
| topic 的标题 | `topics.yaml` | 除切分以外的主循环调用 |
| 图片的内容 | 图片文件 | 没有调用读到，提示词里只有路径 |

## 逐个调用

| 调用 | 读不到、而我们存着的信息 | 对它的判断有没有用 |
|---|---|---|
| 第一级压缩：调用 | 这次调用之前的对话，包括 AI 在同一轮里说的话和用户的请求 | 可能有用。提示词要它写“这次调用想达成什么”，而一条 `cat` 或 `grep` 命令的目的常常只写在 AI 前面那句话里。现在它只能从命令、路径和参数推断 |
| 第一级压缩：结果 | 结果被切块时，其他块的内容；这次调用之前的对话 | 切块时有用：每一块都要对照意图写结论，却看不到其他块。`claude-87eeb4bd-qwen-3d597c7` 的 51 个结果没有一个被切块，所以这一轮里没有影响 |
| 轮次压缩 | 图谱；这一批操作的原文 | 用处小。它只写一段概括，开启这一轮的发言已经说明了这些操作在为什么事服务 |
| 切分 | topic 的标题；窗口以外的发言；图谱节点的原话；图片内容 | topic 标题的用处小，但是给它几乎不占空间。窗口以外的发言在用户指代很久以前的事时有用 |
| 调用 T | 窗口以外的发言；图谱节点的原话；当前工具调用的原文 | 用处小。归属看的是这个单元在继续哪件事，节点的 label 和窗口通常足够 |
| 调用 A（用户信号） | 被用户拒绝的那个工具调用的原文 | 可能有用。提示词要它推断用户为什么叫停，而它只看到这个调用的意图和对象的概括 |
| 调用 B | 候选意图的原话 | 用处中等。`match` 比的是意图本身，label 通常足够；label 是登记时写的标准文本，原话里的限定条件如果没有写进 label，`complete` 就判断不出来 |
| 调用 G | 窗口里每个工具调用归入了哪个聚合；每个候选聚合已有的底层意图 | 很可能有用。它要判断“这个操作是不是在继续某个已有聚合做的事”，但它看到的是聚合的标题和一串没有标聚合编号的工具调用，两者之间的对应关系要靠它自己猜 |
| 调用 L | 已有底层意图各自的操作对象 | 可能有用。提示词要它比较“要做的事和操作对象是否相同”，而 `<已有的底层意图>` 只有意图文本，操作对象只有在那次调用还留在窗口里时才看得到，并且没有和编号对应起来 |
| 调用 C | 窗口以外的节点的原话；聚合里每次调用的意图和对象；聚合观测背后每个结果的概括；窗口以外的未建节点观测 | 有用。问题表第 7 项就是远端意图的原话不在窗口里，evidence 没有地方摘 |
| 调用 D | 工具结果的原文；候选意图的原话；同一个聚合较早的结果（窗口以外的只剩滚动更新的那一句聚合观测） | 很可能有用。结果的概括是第一级压缩对照这次调用自己的意图写的，那时还没有图谱；一个上层意图是否达成，可能取决于概括里没有保留的细节。意图的原话里可能有验收条件，label 只有一句话 |

## 索取出口

`llm.asker` 做出的每个调用都可以带一个出口：模型的回答要么是答案，要么是一份想看的内容的名字清单。代码取出这些内容，放进提示词末尾的 `<补充的内容>`，再问一次。一个任务最多索取 `llm.OFFER_ROUNDS` 轮，之后的调用没有出口，必须回答。出口在 `asker` 里实现，所以第一级压缩、切分和主循环的三处重问循环都不需要知道它：校验不通过或思考顶满而重问时，已经给出的内容保留，索取的轮数不重新计。

出口由任务打开：任务在 `llm.offering(Offer(...))` 的范围内发出调用，`Offer` 写明三件事，一是提示词里告诉模型可以要什么的那句话（`menu`），二是按名字取内容的函数（`fetch`），三是提示词还剩多少 token 可以放出口的说明和取回的内容（`room`）。取回的内容放不下时，那一项写成“提示词放不下这项内容”；名字不存在时，写成“没有这项内容”。出口的说明本身都放不下时，这个调用不带出口。

现在没有任何调用打开出口：每种调用可以索取什么还没有定。
