# 轨迹提取器：概念与存储格式

本文档定义轨迹提取器的概念、存储格式、关系类型和判断原则；提取流程（处理单元、context 组装、LLM 调用和校验）定义在 `docs/workflow.md`。topic 列表 `playground/topics.yaml` 和各个 topic 存储文件 `playground/topics/<topic 编号>.yaml` 的结构以本文档为准，自动提取写到 `--out` 目录下的 `topics.yaml` 和 `topics/` 用的是同样的结构；存储文件、代码或提示词和这两份文档冲突时，先改文档，再改它们。

轨迹提取器的工作方式是：从一段对话的时间线开头开始，依次读取用户说的话、AI 的工具调用，以及环境返回的结果。它从用户的话、AI 对用户说的话和 AI 的工具调用里提取意图，把影响了意图走向的环境结果记为观测，再记录这些节点之间的关系，最后形成一张意图图谱。提取由 `intent_aligner.extract` 自动执行，模型可以是本地 LLM，也可以是 Claude 或 Codex 的模型。`playground/` 里是手工完成的示范提取。

适用范围：目前处理 Claude Code 和 Codex 对话的主时间线。子代理的内部记录（`subagents/` 目录）和上下文压缩后注入的摘要，处理方式都还没有确定。

## 概念

意图图谱的结构参照强化学习的基本框架：

| 对话里的内容 | 强化学习术语 | 意图图谱里的节点 |
|---|---|---|
| 用户说的话，以及用户中断、用户拒绝工具调用 | 任务或目标 | intent，`actor: user` |
| AI 对用户说的话 | action（动作） | intent，`actor: ai` |
| AI 的工具调用 | action（动作） | 底层意图有自己的编号 `L###`，不进图谱；图谱节点是它们所属的 aggregate（意图聚合） |
| 工具结果、任务通知、系统注入的消息 | observation（观测） | observation |
| AI 的思考 | — | 暂时跳过，不读取，也不建节点 |

**意图（intent）**是轨迹中最小的单元。同一个意图的完成标准、作用范围这类属性，要写进这个意图的文本里，不能拆成单独的意图。一个意图在文本里的出现方式有三种：

- 一个意图可以横跨好几个逗号子句，甚至横跨好几个句子。
- 一个子句里可以同时包含好几个深层意图。
- 同一个意图可以在相隔很远的句子里再次出现。

AI 的意图从它的工具调用里提取，提取的是这次调用想达成什么，而不是这次调用的字面内容。比如 AI 执行 `ls projects/somnia-farm`，要记录的意图是“了解 somnia-farm 的目录结构”，而不是“列出目录”。

**发言**指用户亲手发送的一条消息，或者 AI 对用户说的一段话。两种发言用相同的方式处理：都切成段落，每段提取意图，意图都是图谱里的 `I` 节点，用 `actor` 区分是谁说的（`user` 或 `ai`）。比如 AI 说“3070 没问题，原因在校验。我继续查这个校验。”，要记录两个 AI 意图：“告诉用户 run 卡住的原因在校验，不在 3070”和“继续排查这个校验”。AI 说的话不能只当作上下文，因为那样它报告的结论、提出的计划和问用户的问题都不会出现在图谱里。

用户的意图和 AI 的意图即使内容相同，也是两个节点：AI 复述或者接下用户的请求时，登记成一个新的 AI 意图，再用边和用户的意图相连，而不是并进用户的意图节点。如果并进去，图谱里就看不出 AI 说过这句话。

**用户信号**是用户不通过打字表达的表态，有两种：一种是用户按 ESC 中断 AI，记录里留下 `[Request interrupted by user]` 或 `[Request interrupted by user for tool use]`；另一种是用户拒绝某个工具调用，记录里留下一条以 “The user doesn't want to …” 开头的错误工具结果，有时后面还附有用户写的理由。这两种都是用户的直接表态，所以按用户意图处理，不按观测处理。Claude Code 内置安全检查拒绝的工具调用（错误信息里写明 “denied by a built-in Claude Code safety check”）不是用户的表态，按观测处理。

**观测（observation）**是环境返回给对话参与者的信息。观测分成两种：一种是 AI 某个动作的执行结果，即工具结果；另一种是环境主动推送的状态变化，比如任务通知、系统注入的消息。

**工具结果和产生它的调用是一对。** 每个工具结果通过 `tool_use_id` 对应一次工具调用，所以（调用，结果）成对完整地存放在图外的 `meta.tool_pairs` 里，按调用所属的聚合列出。一个调用的意图分属几个聚合时，这一对在每个聚合下各列一次。

**聚合的观测（aggregate_observation）**是一个聚合到目前为止的结果，和聚合的标题在同一层：标题说这一串操作要做成什么，聚合的观测说这一串操作现在怎么样了。每个聚合在图里只有一个聚合的观测节点，所以图的大小随聚合的数量增长，不随工具调用的次数增长。聚合里只有一对时，节点的文本直接是这个结果的概括；之后每来一对，模型把上一版文本和新结果合成一句新的文本。图里只放最新的情况，变化过程在 `meta.tool_pairs` 里。

任务通知和系统消息没有配对的调用，也就没有聚合可以归属，它们仍然各自成为观测节点（observation）：
只记录影响了轨迹的这类观测，也就是至少有一条 `satisfies`、`blocks` 或 `triggers` 边的观测。没有这些边的不建节点。工具结果的提取失败，或者产生它的调用没有聚合时，这个结果也建成一个带 `needs_review: true` 的观测节点，即使没有任何边，这样失败的观测不会被静默丢掉。

**意图的状态**只有两种，由图上的边算出来，不单独存储：有 `satisfies` 边指向这个意图或聚合时是“已完成”，否则是“待完成”。“待完成”的准确含义是没有观测表明它已经做成。意图允许一直不被完成，对话结束时仍然待完成是如实的结果，不是提取错误。`blocks` 不改变状态。聚合的观测更新时，这个节点原来的 `satisfies` 和 `blocks` 边换成新的，所以状态可以退回待完成。一个聚合完成不会让它服务的意图自动完成，那个意图是否完成要看有没有观测直接表明。

**意图聚合（aggregate）**把工具调用的底层意图打包成一个意图。意图分两个层级：发言的意图、用户信号的意图和意图聚合在同一层，叫对话层；工具调用的底层意图低于这一层，比如“读 workbench-guide.md 的第 47 到 140 行”这样的具体操作。一个聚合用一句标准文本说明这些操作合起来在做什么，比如“调查 somnia-farm 的文档和目录结构”。图谱里只记录对话层：工具调用的底层意图不是图谱节点，它们完整地记录在工具调用段落里，所以每段内容的信息仍然由它的意图完整描述。规则如下：

- 聚合只作用于工具调用，是 topic 里的一段工具操作，范围比 topic 小。一个聚合不能涵盖 topic 的全部操作，能涵盖就说明粒度太粗，这一点在聚合诞生、写标题时就要把关。每个步骤各算一个聚合同样不对，那样聚合就和底层意图没有区别了。
- 只有工具调用的底层意图进入聚合。发言的意图和用户信号的意图不使用聚合。
- 一个底层意图只属于一个聚合，同一个工具调用的几个意图可以分属不同的聚合。
- 底层意图的集合不因为聚合而消失：每个底层意图有自己的编号，topic 文件的 `meta.tool_intents` 记录每个聚合包含哪些底层意图。这个集合用来去重：同一个底层意图再次出现时沿用原来的编号，所以同一个编号可以出现在多个段落里。去重只在同一个聚合内部进行。
- 聚合不能再被聚合。
- 聚合是意图节点的一种，图谱里的边把它当作意图：关系类型表里的 intent 既可以是发言或用户信号的意图（用户的和 AI 的都算），也可以是聚合。

**段落（span）**是时间线上一段连续的内容，在这段内容里对话层的意图集合保持不变：发言段落和用户信号段落看它的意图集合，工具调用段落看它所属的聚合集合。段落有四种：

- **用户文本段落**（`user_text`）：用户消息正文中的一段连续文本，由切分确定（见 `docs/workflow.md` 的“发言的切分”）。
- **AI 文本段落**（`ai_text`）：AI 对用户说的一段话里的一段连续文本，同样由切分确定。
- **工具调用段落**（`tool_calls`）：AI 连续发出的一个或多个工具调用。两个工具调用之间如果出现了一次发言或者一个用户信号，它们就不算连续。中间夹着的工具结果不影响连续性。
- **用户信号段落**（`user_signal`）：一次用户中断，或者一次用户拒绝工具调用。每个用户信号单独成为一个段落。

划分段落的规则如下：

- **合并**：相邻内容如果属于同一个 topic，并且对话层的意图集合完全相同，就合并成一个段落，因为重复记录相同的意图包只会制造冗余信息。工具调用段落的合并比较的是聚合集合，段落的 `intents` 记录各个调用的全部底层意图。
- **切开**：相邻内容的意图集合只要有任何不同，就切成不同的段落，即使它们在语法上属于同一个句子。比如“我接下来要你用我已经搭好的部分的基础设施，自己运用工具的所有功能（参数探索）和已经搭建好的wf ,来生成一段音乐的mv。”这一句，三个逗号子句的意图集合分别是 {I003}、{I004, I003}、{I002}，所以记成三个段落。
- **同一个意图出现在多个段落里不算冗余**：每个段落只用编号引用意图，意图文本只在注册表里存一份。比如上例的 I003 同时出现在第一和第二个子句里，两个段落各自引用 I003。
- **没有意图的内容并入相邻段落**：本身没有意图的内容，比如单独的“好的，”、粘贴进来的日志或表格，并入用到它、说明它或回应它的那一段。合并只在同一次发言内部进行。整次发言都没有意图时，这次发言单独成为一个占位段落，它的 `intents` 是空列表。
- **校验失败的单元不参与合并**：提取时重试仍然失败、被标记为 `needs_review` 的单元，没有可靠的意图集合，所以单独成为一个段落。

**段落边界的粒度**：用户文本段落和 AI 文本段落的边界可以落在任何字符上，一个句子可以切成几段，几句话也可以是一段，只看意图集合有没有变。段落末尾紧跟的空格和换行归入这个段落，所以下一段从下一个非空白字符开始。

**覆盖**：一次发言的所有文本段落必须首尾相接地覆盖这次发言的整个正文，中间不能有遗漏，也不能有重叠；没有意图的内容通过并入相邻段落被覆盖。每一个工具调用都必须属于某一个工具调用段落，每一个用户信号都必须属于某一个用户信号段落。每一段内容的信息都必须被它的意图完整描述。

**topic** 是对话里一件独立的事情，它决定了意图图谱的范围。topic 和 session 之间没有固定的对应关系：一个 session 里可以穿插好几个互不相干的 topic，一个 topic 也可以延续好几个 session。每个 topic 有一个自己的存储文件，存放属于这个 topic 的段落和意图图谱。所有 topic 登记在 topic 列表里，这份列表会放进 LLM 每次调用的 header，所以模型在输出结构化结果时知道当前操作属于哪个 topic。

topic 的规则如下：

- 每个段落、每个节点只属于一个 topic。一次发言的段落可以分属不同的 topic，这时这次发言的段落分散在几个 topic 文件里。
- 边的两端必须属于同一个 topic，因为不同的 topic 互不相干。
- 节点编号和段落编号在所有 topic 之间全局唯一，由代码统一分配。这样跨文件做覆盖检查时，编号不会冲突。
- topic 归属无法确定的单元，写进未归属文件 `topics/unassigned.yaml`（程序输出在 `--out` 目录下），它的格式和普通 topic 文件相同，但不登记在 topic 列表里。

**意图图谱**：节点是意图、聚合、聚合的观测和观测，边是节点之间的关系，结构参照 graphviz 的节点和边。图谱以意图为中心，观测是意图走向的环境依据。意图文本只描述意图本身；“为了做 B 才做 A”这类关系不写进意图文本，而是记录成边。

## 存储格式

本项目所有文件里记录的路径，包括存储文件、`corpus/index.json`、合并记录里的 `_merge.file` 和文档里的引用，都相对于工具根目录 `/media/spikezz/v/Project/intent-aligner`。

topic 列表是 `playground/topics.yaml`：

```yaml
topics:
  - id: T001
    title: topic 的标题，一句完整的话
    file: playground/topics/T001.yaml
```

每个 topic 的存储文件是 `playground/topics/<topic 编号>.yaml`，`meta.topic` 是这个文件所属的 topic 编号，`meta.graph` 存储这个 topic 的意图图谱：

```yaml
meta:
  topic: T001
  graph:
    nodes:
      I001:
        type: intent
        actor: user         # user 或 ai：说出这个意图的一方
        label: 意图的标准文本
      G001:
        type: aggregate
        label: 这些工具操作合起来在做什么
      O002:
        type: aggregate_observation
        aggregate: G001       # 这是哪个聚合的观测
        label: 这个聚合现在的情况
      O001:
        type: observation
        label: 任务通知或系统消息的概括；提取失败时是工具结果的概括
        source:               # 观测所在的原始记录
          uuid: <记录 uuid>
          tool_use_id: <对应的工具调用 id>   # 只有工具结果才有
        needs_review: true    # 可选，只在提取校验失败时出现
    edges:
      - from: I001
        to: I002
        relation: serves
        span: S002            # 这条关系是在哪个段落里确立的；satisfies 和 blocks 来自观测，观测没有段落，所以没有这个字段
        evidence: "原文片段"
  tool_pairs:                 # 聚合 -> 成对的（调用，结果）；不在 graph 里，所以不进 header
    G001:
      - tool_use_id: <工具调用 id>
        call: "代码按固定格式渲染的调用原文"
        result: "第一级压缩给出的结果概括"
  tool_intents:               # 聚合 -> 底层意图编号 -> 底层意图的文本；不在 graph 里，所以不进 header
    G001:
      L001: 这个底层意图的文本

spans:
  - id: S001
    kind: user_text
    source:                   # 用于回查原始记录
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      uuid: <记录 uuid>
      timestamp: "<柏林本地时间>"
    chars: [0, 67]            # 段落在发言正文中的字符区间，左闭右开
    text: "段落原文"
    intents:
      - id: I001
        evidence: "支撑这个意图的原文片段"
        explicit: true        # true 表示明说；false 表示推断，推断依据写进 note
        note: "可选；explicit 为 false 时必填，写推断依据"
    note: "可选，只在人工示范时填写，说明段落边界为什么划在这里"
    needs_review: true        # 可选，只在提取校验失败时出现
  - id: S002
    kind: tool_calls
    source:
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      tool_use_ids: [<工具调用 id>, ...]
      timestamp: "<第一个调用的柏林本地时间>"
    text: "代码按固定格式渲染的调用原文，比如 Bash: ls projects/somnia-farm"
    intents:                  # 每项是一个底层意图，id 是它自己的编号，所属聚合和文本查 meta.tool_intents
      - id: L001
        evidence: "支撑这个意图的调用内容"
        explicit: false
  - id: S003
    kind: user_signal
    source:
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      uuid: <记录 uuid>
      tool_use_id: <被拒绝的工具调用 id>   # 只有拒绝工具调用才有
      timestamp: "<柏林本地时间>"
    text: "[Request interrupted by user]"
    intents:
      - id: I003
        evidence: "[Request interrupted by user]"
        explicit: false
  - id: S004
    kind: ai_text             # 字段和 user_text 相同
    source:
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      uuid: <AI 这段话所在记录的 uuid>
      timestamp: "<柏林本地时间>"
    chars: [0, 58]            # 段落在这段话正文中的字符区间，左闭右开
    text: "段落原文"
    intents:
      - id: I004              # 这个节点的 actor 是 ai
        evidence: "支撑这个意图的原文片段"
        explicit: true
```

- 每个 topic 文件的 `meta.graph.nodes` 同时也是这个 topic 的意图注册表。每个意图只登记一次，标准文本只写在注册表这一处。这样同一个意图跨段落出现时，引用它的所有段落拿到的都是同一份文本。
- 段落只通过 `id` 引用意图，不引用观测。观测只通过边和意图相连。工具调用段落的 `id` 引用的是底层意图的编号，底层意图的文本只写在 `meta.tool_intents` 这一处。
- `evidence` 是原文的摘录。摘录可以用 `…` 省略中间的部分，但是被 `…` 分开的每一个片段都必须原样出现在原文里，并且按原文的先后顺序排列。这样代码可以机械地校验 `evidence`。
- `evidence`、`explicit`、`note` 描述的是这个意图在这一段里是怎么出现的，所以每次出现都单独记录。对工具调用段落来说，`explicit: true` 表示 AI 在调用中写明了目的，比如 Bash 调用的 `description` 字段；否则是推断。
- **消息正文**：用户消息的内容如果是纯字符串，正文就是这个字符串。如果内容是列表（带图片的消息是一个文本块加若干图片块），正文就是其中唯一的文本块。文本块不止一个时，提取应当报错停止，因为目前语料里没有这种情况，`chars` 也还没有为它定义。图片本身的内容目前不读取；文本块里的 `[Image #N]` 占位符作为原文的一部分保留。AI 发言的正文是这段话的文本：Claude 的一个 `text` 块，或者 Codex 一条 `assistant` 消息里各文本块用换行连起来的全文。
- `chars`、`tool_use_ids` 让脚本可以机械地检查覆盖是否完整。检查一次发言的覆盖时，要把所有 topic 文件和未归属文件里 `source.uuid` 指向这次发言的段落合起来检查。
- 节点编号的前缀表示类型：`I` 是发言或用户信号的意图，用户的和 AI 的都用 `I`，由 `actor` 区分；`G` 是意图聚合，`O` 是观测和聚合的观测。`L` 是工具调用的底层意图，它不是图谱节点，编号同样全局递增。

**关系类型**是初始的一套词表，会在示范过程中根据实际遇到的关系增删：

| relation | 方向 | 含义 |
|---|---|---|
| `serves` | intent → intent | from 是实现 to 的手段；一个意图给已有意图补充了细节时，它也服务于那个已有意图，起点是新意图，终点是已有意图 |
| `satisfies` | observation → intent | from 这个观测表明 to 这个意图已经达成 |
| `blocks` | observation → intent | from 这个观测表明 to 这个意图没有达成，或者遇到了障碍 |
| `triggers` | observation → intent | from 这个观测引出了 to 这个新意图；to 不能是产生这个观测的聚合 |

`satisfies` 和 `blocks` 边的 `evidence` 是观测所在记录的编号，而且记的是这条边第一次出现时的那个结果，后续结果更新观测时不改它：工具结果是 `tool_use_id`，其他观测是记录的 uuid，因为这些边不是从对话原文里摘录出来的，文字已经在起点节点上。`satisfies` 和 `blocks` 记录的是环境给出的事实。用户对 AI 工作的评价，比如打分或者说“这个不对”，在性质上是评价信号，不属于观测；这类评价是否单独建节点类型，等语料里读到时再定。

## 判断原则

以下原则是 LLM 在各次调用中做判断时遵循的标准，调用的具体问法见 `docs/workflow.md`。

- 判断一个意图是新意图还是已有意图，要看意图本身是否相同，不能看措辞是否相似。同一个意图换一种说法再出现时，仍然要引用原来的编号。这个判断只在同一方的意图之间进行：AI 的意图只和 AI 的意图比较，用户的意图只和用户的意图比较。
- 一个单元如果给已有意图补充了新的信息，比如指定了具体用哪个文件，就不能只引用已有意图，因为那样新信息就丢了。这时要登记一个新意图，再加一条从已有意图指向新意图的 `refines` 边。
- 意图文本和观测文本都要写成完整的一句话，并且脱离原文也能读懂。
- 证据强度要分开记录：明说的意图和推断的意图用 `explicit` 字段区分，绝不能把推断写成明说。
