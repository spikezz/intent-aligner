# 轨迹提取器：概念与存储格式

本文档定义轨迹提取器的概念、存储格式、关系类型和判断原则；提取流程（处理单元、context 组装、LLM 调用和校验）定义在 `docs/workflow.md`。topic 列表 `playground/topics.yaml` 和各个 topic 存储文件 `playground/topics/<topic 编号>.yaml` 的结构以本文档为准；存储文件、代码或提示词和这两份文档冲突时，先改文档，再改它们。

轨迹提取器的工作方式是：从一段对话的时间线开头开始，依次读取用户说的话、AI 的工具调用，以及环境返回的结果。它从用户的话和 AI 的工具调用里提取意图，把影响了意图走向的环境结果记为观测，再记录这些节点之间的关系，最后形成一张意图图谱。最终由本地 LLM 执行提取。目前处在示范阶段：先由 Claude 以最佳质量手工完成提取，产出的结果作为本地 LLM 的样例；同时，这个过程也用来把推理任务的定义打磨清楚。

适用范围：目前处理 Claude Code 和 Codex 对话的主时间线。子代理的内部记录（`subagents/` 目录）和上下文压缩后注入的摘要，处理方式都还没有确定。

## 概念

意图图谱的结构参照强化学习的基本框架：

| 对话里的内容 | 强化学习术语 | 意图图谱里的节点 |
|---|---|---|
| 用户说的话，以及用户中断、用户拒绝工具调用 | 任务或目标 | intent，`actor: user` |
| AI 的工具调用 | action（动作） | 底层意图记在工具调用段落里，图谱节点是它们所属的 aggregate（意图聚合） |
| 工具结果、任务通知、系统注入的消息 | observation（观测） | observation |
| AI 的思考 | — | 暂时跳过，不读取，也不建节点 |
| AI 对用户说的话 | — | 只作为 context，不建节点 |

**意图（intent）**是轨迹中最小的单元。同一个意图的完成标准、作用范围这类属性，要写进这个意图的文本里，不能拆成单独的意图。一个意图在文本里的出现方式有三种：

- 一个意图可以横跨好几个逗号子句，甚至横跨好几个句子。
- 一个子句里可以同时包含好几个深层意图。
- 同一个意图可以在相隔很远的句子里再次出现。

AI 的意图从它的工具调用里提取，提取的是这次调用想达成什么，而不是这次调用的字面内容。比如 AI 执行 `ls projects/somnia-farm`，要记录的意图是“了解 somnia-farm 的目录结构”，而不是“列出目录”。

**用户信号**是用户不通过打字表达的表态，有两种：一种是用户按 ESC 中断 AI，记录里留下 `[Request interrupted by user]` 或 `[Request interrupted by user for tool use]`；另一种是用户拒绝某个工具调用，记录里留下一条以 “The user doesn't want to …” 开头的错误工具结果，有时后面还附有用户写的理由。这两种都是用户的直接表态，所以按用户意图处理，不按观测处理。Claude Code 内置安全检查拒绝的工具调用（错误信息里写明 “denied by a built-in Claude Code safety check”）不是用户的表态，按观测处理。

**观测（observation）**是环境返回给对话参与者的信息。观测分成两种：一种是 AI 某个动作的执行结果，即工具结果；另一种是环境主动推送的状态变化，比如任务通知、系统注入的消息。观测和意图有两点不同：

1. **观测不去重**。每个观测都是只发生一次的事件，所以每出现一次就是一个新节点，不需要和已有节点比较。
2. **只记录影响了轨迹的观测**。一个观测至少要有一条 `satisfies`、`blocks` 或 `triggers` 边，才建成节点。只产生了 `produces` 边的观测没有改变任何意图的走向，所以不记录。唯一的例外是提取时校验失败的观测：它会建成一个带 `needs_review: true` 的节点，即使没有任何边，这样失败的观测不会被静默丢掉。

**意图聚合（aggregate）**把工具调用的底层意图打包成一个意图。意图分两个层级：用户发言的意图和意图聚合在同一层，叫对话层；工具调用的底层意图低于这一层，比如“读 workbench-guide.md 的第 47 到 140 行”这样的具体操作。一个聚合用一句标准文本说明这些操作合起来在做什么，比如“调查 somnia-farm 的文档和目录结构”。图谱里只记录对话层：工具调用的底层意图不是图谱节点，它们完整地记录在工具调用段落里，所以每段内容的信息仍然由它的意图完整描述。规则如下：

- 只有工具调用的底层意图进入聚合。用户的意图和 AI 的回复不使用聚合。
- 一个底层意图只属于一个聚合，同一个工具调用的几个意图可以分属不同的聚合。
- 聚合不能再被聚合。
- 聚合是意图节点的一种，图谱里的边把它当作意图：关系类型表里的 intent 既可以是用户的意图，也可以是聚合。

**段落（span）**是时间线上一段连续的内容，在这段内容里对话层的意图集合保持不变：用户段落看它的意图集合，工具调用段落看它所属的聚合集合。段落有三种：

- **用户文本段落**（`user_text`）：用户消息正文中的一段连续文本，由切分确定（见 `docs/workflow.md` 的“用户消息的切分”）。
- **工具调用段落**（`tool_calls`）：AI 连续发出的一个或多个工具调用。两个工具调用之间如果出现了用户文本、用户信号或者一条 AI 对用户说的话，它们就不算连续。中间夹着的工具结果不影响连续性。
- **用户信号段落**（`user_signal`）：一次用户中断，或者一次用户拒绝工具调用。每个用户信号单独成为一个段落。

划分段落的规则如下：

- **合并**：相邻内容如果属于同一个 topic，并且对话层的意图集合完全相同，就合并成一个段落，因为重复记录相同的意图包只会制造冗余信息。工具调用段落的 `intents` 是各个调用的底层意图的全部记录。
- **切开**：相邻内容的意图集合只要有任何不同，就切成不同的段落，即使它们在语法上属于同一个句子。比如“我接下来要你用我已经搭好的部分的基础设施，自己运用工具的所有功能（参数探索）和已经搭建好的wf ,来生成一段音乐的mv。”这一句，三个逗号子句的意图集合分别是 {I003}、{I004, I003}、{I002}，所以记成三个段落。
- **同一个意图出现在多个段落里不算冗余**：每个段落只用编号引用意图，意图文本只在注册表里存一份。比如上例的 I003 同时出现在第一和第二个子句里，两个段落各自引用 I003。
- **没有意图的内容并入相邻段落**：本身没有意图的内容，比如单独的“好的，”、粘贴进来的日志或表格，并入用到它、说明它或回应它的那一段。合并只在同一条消息内部进行。整条消息都没有意图时，这条消息单独成为一个占位段落，它的 `intents` 是空列表。
- **校验失败的单元不参与合并**：提取时重试仍然失败、被标记为 `needs_review` 的单元，没有可靠的意图集合，所以单独成为一个段落。

**段落边界的粒度**：用户文本段落的边界可以落在任何字符上，一个句子可以切成几段，几句话也可以是一段，只看意图集合有没有变。段落末尾紧跟的空格和换行归入这个段落，所以下一段从下一个非空白字符开始。

**覆盖**：一条用户消息的所有用户文本段落必须首尾相接地覆盖整个正文，中间不能有遗漏，也不能有重叠；没有意图的内容通过并入相邻段落被覆盖。每一个工具调用都必须属于某一个工具调用段落，每一个用户信号都必须属于某一个用户信号段落。每一段内容的信息都必须被它的意图完整描述。

**topic** 是对话里一件独立的事情，它决定了意图图谱的范围。topic 和 session 之间没有固定的对应关系：一个 session 里可以穿插好几个互不相干的 topic，一个 topic 也可以延续好几个 session。每个 topic 有一个自己的存储文件，存放属于这个 topic 的段落和意图图谱。所有 topic 登记在 topic 列表里，这份列表会放进 LLM 每次调用的 header，所以模型在输出结构化结果时知道当前操作属于哪个 topic。

topic 的规则如下：

- 每个段落、每个节点只属于一个 topic。一条用户消息的段落可以分属不同的 topic，这时这条消息的段落分散在几个 topic 文件里。
- 边的两端必须属于同一个 topic，因为不同的 topic 互不相干。
- 节点编号和段落编号在所有 topic 之间全局唯一，由代码统一分配。这样跨文件做覆盖检查时，编号不会冲突。
- topic 归属无法确定的单元，写进未归属文件 `topics/unassigned.yaml`（程序输出在 `--out` 目录下），它的格式和普通 topic 文件相同，但不登记在 topic 列表里。

**意图图谱**：节点是意图和观测，边是节点之间的关系，结构参照 graphviz 的节点和边。图谱以意图为中心，观测是意图走向的环境依据。意图文本只描述意图本身；“为了做 B 才做 A”这类关系不写进意图文本，而是记录成边。

## 存储格式

本项目所有文件里记录的路径，包括存储文件、`corpus/index.json`、合并记录里的 `_merge.file` 和文档里的引用，都相对于工具根目录 `/media/spikezz/v/Project/intent-aligner`。

topic 列表是 `playground/topics.yaml`：

```yaml
topics:
  - id: T001
    title: topic 的标题，一句完整的话
    file: playground/topics/T001.yaml
```

每个 topic 的存储文件是 `playground/topics/<topic 编号>.yaml`，`meta.topic` 是这个文件所属的 topic 编号，`meta.graph` 存储这个 topic 的意图图谱：

```yaml
meta:
  topic: T001
  graph:
    nodes:
      I001:
        type: intent
        actor: user
        label: 意图的标准文本
      G001:
        type: aggregate
        label: 这些工具操作合起来在做什么
      O001:
        type: observation
        label: 观测内容的概括
        source:               # 观测所在的原始记录
          uuid: <记录 uuid>
          tool_use_id: <对应的工具调用 id>   # 只有工具结果才有
        needs_review: true    # 可选，只在提取校验失败时出现
    edges:
      - from: I001
        to: I002
        relation: prerequisite
        span: S002            # 这条关系是在哪个段落里确立的
        evidence: "原文片段"

spans:
  - id: S001
    kind: user_text
    source:                   # 用于回查原始记录
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      uuid: <记录 uuid>
      timestamp: "<柏林本地时间>"
    chars: [0, 67]            # 段落在消息正文中的字符区间，左闭右开
    text: "段落原文"
    intents:
      - id: I001
        evidence: "支撑这个意图的原文片段"
        explicit: true        # true 表示明说；false 表示推断，推断依据写进 note
        note: "可选；explicit 为 false 时必填，写推断依据"
    note: "可选，只在人工示范时填写，说明段落边界为什么划在这里"
    needs_review: true        # 可选，只在提取校验失败时出现
  - id: S002
    kind: tool_calls
    source:
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      tool_use_ids: [<工具调用 id>, ...]
      timestamp: "<第一个调用的柏林本地时间>"
    text: "代码按固定格式渲染的调用原文，比如 Bash: ls projects/somnia-farm"
    intents:                  # 每项是一个底层意图，id 是它所属的聚合，同一个聚合可以出现多次
      - id: G001
        text: "这个底层意图的文本"
        evidence: "支撑这个意图的调用内容"
        explicit: false
  - id: S003
    kind: user_signal
    source:
      merged_file: corpus/merged/claude-5a1f0c1a.jsonl
      session: <session id>
      uuid: <记录 uuid>
      tool_use_id: <被拒绝的工具调用 id>   # 只有拒绝工具调用才有
      timestamp: "<柏林本地时间>"
    text: "[Request interrupted by user]"
    intents:
      - id: I003
        evidence: "[Request interrupted by user]"
        explicit: false
```

- 每个 topic 文件的 `meta.graph.nodes` 同时也是这个 topic 的意图注册表。每个意图只登记一次，标准文本只写在注册表这一处。这样同一个意图跨段落出现时，引用它的所有段落拿到的都是同一份文本。
- 段落只通过 `id` 引用意图，不引用观测。观测只通过边和意图相连。工具调用段落的 `id` 引用的是聚合，同时带上底层意图自己的 `text`，因为底层意图在图谱里没有节点。
- `evidence` 是原文的摘录。摘录可以用 `…` 省略中间的部分，但是被 `…` 分开的每一个片段都必须原样出现在原文里，并且按原文的先后顺序排列。这样代码可以机械地校验 `evidence`。
- `evidence`、`explicit`、`note` 描述的是这个意图在这一段里是怎么出现的，所以每次出现都单独记录。对工具调用段落来说，`explicit: true` 表示 AI 在调用中写明了目的，比如 Bash 调用的 `description` 字段；否则是推断。
- **消息正文**：用户消息的内容如果是纯字符串，正文就是这个字符串。如果内容是列表（带图片的消息是一个文本块加若干图片块），正文就是其中唯一的文本块。文本块不止一个时，提取应当报错停止，因为目前语料里没有这种情况，`chars` 也还没有为它定义。图片本身的内容目前不读取；文本块里的 `[Image #N]` 占位符作为原文的一部分保留。
- `chars`、`tool_use_ids` 让脚本可以机械地检查覆盖是否完整。检查一条用户消息的覆盖时，要把所有 topic 文件和未归属文件里 `source.uuid` 指向这条消息的段落合起来检查。
- 节点编号的前缀表示类型：`I` 是用户的意图，`G` 是意图聚合，`O` 是观测。

**关系类型**是初始的一套词表，会在示范过程中根据实际遇到的关系增删：

| relation | 方向 | 含义 |
|---|---|---|
| `prerequisite` | intent → intent | 要做 to，必须先完成 from |
| `serves` | intent → intent | from 是实现 to 的手段 |
| `refines` | intent → intent | to 把 from 具体化，或者给 from 加上限定；from 是已有的意图，to 是新意图 |
| `supersedes` | intent → intent | to 修正或取代了 from；from 是旧意图，to 是新意图 |
| `produces` | intent → observation | from 这个动作的执行产生了 to 这个观测；工具调用有几个意图，就从每个意图各连一条 |
| `satisfies` | observation → intent | from 这个观测表明 to 这个意图已经达成 |
| `blocks` | observation → intent | from 这个观测表明 to 这个意图没有达成，或者遇到了障碍 |
| `triggers` | observation → intent | from 这个观测引出了 to 这个新意图 |

意图从 A 转向 B 时，如果转向是由某个观测引起的，图谱里要同时记录两条边：从 A 指向 B 的 `supersedes` 边，以及从这个观测指向 B 的 `triggers` 边。用户拒绝工具调用时，通常有一条从被拒绝调用的意图指向用户信号意图的 `supersedes` 边。

`satisfies` 和 `blocks` 记录的是环境给出的事实。用户对 AI 工作的评价，比如打分或者说“这个不对”，在性质上是评价信号，不属于观测；这类评价是否单独建节点类型，等语料里读到时再定。

## 判断原则

以下原则是 LLM 在各次调用中做判断时遵循的标准，调用的具体问法见 `docs/workflow.md`。

- 判断一个意图是新意图还是已有意图，要看意图本身是否相同，不能看措辞是否相似。同一个意图换一种说法再出现时，仍然要引用原来的编号。
- 一个单元如果给已有意图补充了新的信息，比如指定了具体用哪个文件，就不能只引用已有意图，因为那样新信息就丢了。这时要登记一个新意图，再加一条从已有意图指向新意图的 `refines` 边。
- 意图文本和观测文本都要写成完整的一句话，并且脱离原文也能读懂。
- 证据强度要分开记录：明说的意图和推断的意图用 `explicit` 字段区分，绝不能把推断写成明说。
